# 会话最新记录与滚动验收

日期：2026-11-01。Remote 0.2.13，正式管理器 0.2.1 无变更。

## 问题与行为

进入会话时，内存和设备快照会先展示之前的轮次，主机两秒内的干净缓存
也可能被直接复用。首次读取结束到原生订阅接入之间的变化缺少再次核对；
刷新期间的新完成事件还可能因已有刷新而被忽略。这些路径可以造成
“页面已打开，但最新轮次没有出现”的割裂感，不等于原生历史已经丢失。

新选中的主会话直接请求 fresh 正文和计时，等待原生页再展示消息。
主机对这两种 fresh 请求实际重新读取原生数据，仍共享相同的进行中请求。
同一聊天重新核对保留已显示内容；读取失败才使用缓存回退。
首次过期响应在等待下一次读取时不提前显示；第二次仍过期则保留未同步
状态及重试入口。原生 resume 成功后再核对一次，刷新期间的完成事件
合并为后续补读。返回前台的会话末尾核对使用独立的 15 秒冷却，
全任务列表仍为五分钟；历史跳转窗口不会被替换。

滚动时的阅读锚点捕获按动画帧合并，长回复内部按有序位置二分，
避免逐条测量前方消息。轮次导航的观察器也按帧测量，滚动定位使用二分。
保留实际布局高度、原生历史分页、阅读位置、过程展开及返回最新行为。

## 浏览器结果

Chrome 合成数据使用实际 ThreadTimeline、导航、完整样式和
`scripts/acceptance-viewports.json` 的八种尺寸，包括 402×874、
874×402、DPR 3 及 320×568。没有连接 Desktop 或发送模型请求。

- 180 轮长回复：初始和追加四轮后均定位底部，末条为第 184 轮。
- 阅读中补入历史、追加消息：同一锚点偏移最多 0.5 CSS 像素，
  不被拉回底部；点击返回最新后底部距离为零。
- 执行过程展开和折叠均生效；触摸事件保持按住期间不提交历史，
  松开并静止后只提交一次。此项为浏览器合成事件。
- 八种尺寸均无 pageerror。

2500 条运行中 commentary 的单个长回复，在 4 倍 CPU 降速下，
120 次锚点捕获的均值如下。基线与最终代码使用相同数据、完整样式和浏览器。

| 尺寸 | 修改前 | 修改后 |
| --- | --- | --- |
| 1440×900 | 9.31 ms | 0.48 ms |
| 402×874，DPR 3 | 9.36 ms | 0.51 ms |
| 八种尺寸范围 | 8.89–10.04 ms | 0.48–0.55 ms |

普通 180 轮程序滚动中，前后均无超过 50 ms 的采样帧，整体帧耗时
没有一致显著改善。上述数字证明锚点测量开销下降，不是整机 FPS 提升比例。
本地合成 fixture、JSON 和截图保留于忽略的
`output/playwright/chat-loading/`，不含真实聊天。

## 边界

最新读取和订阅接入顺序由 hook 与主机回归测试验证；浏览器测试主要覆盖
真实时间线组件，不等于完整登录链路或用户具体会话已经现场复现。
网络慢时仍需等待原生最新页，已有超时、重试和失败回退继续生效。
没有虚拟化或删除历史，也没有更改消息内容和原生计时来源。

真实 iPhone Safari、主屏幕应用、Wi-Fi／5G、物理触控及已登录 macOS
仍需独立验收。健康检查只证明服务和 Desktop 通道就绪，
不能单独证明某个会话的最新轮次和设备滚动已经通过。
