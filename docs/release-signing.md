# 发布签名运维

Remote 0.2.23 / manager 0.2.4 开始要求 Ed25519 发布者签名；Remote 0.2.38
已于 2026-11-11 使用同一固定公钥完成正式发布与部署收尾。
这是运行包及源码更新的真实性校验，与暂停中的 manager AU 自更新、
macOS 应用代码签名和公证分别管理。

## 信任链

`desktop/release-keys.mjs` 只保存可信公钥。运行包清单签名覆盖版本、仓库、
源提交、平台、归档摘要、文件摘要及源码基线。下载源无论是项目分发域名
还是官方 GitHub，都必须通过同一个固定公钥验证；同源元数据和哈希自洽不再足够。

源码回退也先验证对应版本签名身份，checkout 的提交必须完全相同。
缺失、篡改、未知密钥的清单会阻止更新，不提供跳过开关。
公钥最初随可信安装包进入主机；用户必须从可信渠道完成首次安装。

## 密钥与 CI

`node scripts/init-release-signing.mjs` 创建或复用当前操作者的仓库外私钥，
仅将公钥写入源码。Windows 保存于用户 LocalAppData 下的
`CodexRemote/release-signing/`，目录 ACL 限制为当前用户；
其他系统使用用户私有数据目录并限制权限。

私钥是 PEM 格式，通过 GitHub Actions 的 `RELEASE_SIGNING_KEY` secret 注入
runtime 工作流。不要将其放入 `.env`、仓库、工作流文本、日志或公开附件。
初始化脚本不会上传 secret。2026-11-08 经发布授权已配置 GitHub secret。
正式 runtime 工作流 `43016530341` 在 Windows/macOS 均通过。
两个正式清单已用固定公钥独立验签，签名提交均为
`817e20e8abeb404ae8569acf82d4286a075b4bfb`，完整源码树与标签一致。

正式发布顺序：

1. 审核并提交包含可信公钥的源码，确认版本和源提交。
2. 在私密界面配置 `RELEASE_SIGNING_KEY`，保留受限访问的离线备份。
3. 运行版本、全量行为、构建和打包验收。`runtime:pack` 要求源码与 HEAD 一致，
   缺少私钥或签名不匹配固定公钥立即失败。
4. 发布归档及其签名 manifest，复核两个平台的签名、归档和文件摘要；
   再按原发布流程更新分发快照、边缘资源及授权安装。
5. 分别记录源码、GitHub Release、下载分发、Remote 安装与 manager 安装结果。

现有 manager 0.2.3 及更早版本不会凭 Remote 后端升级获得新校验器。
请使用已发布的 manager 0.2.9 安装包单独升级。
新校验器会拒绝过去没有签名的运行包；不能为兼容旧包而关闭验证。

## 轮换与恢复

正常轮换应先通过当前可信渠道发布同时信任新旧公钥的版本，
确认安装覆盖后，再用新私钥签名，最后在后续版本移除旧公钥。
在隔离环境生成新密钥；不要在现用工作区直接运行初始化脚本覆盖信任根。

私钥丢失且无可信备份时不能给原密钥补签，也不能自动信任下载站提供的新公钥。
应通过人工核实的新 manager 安装包或受控源升级重新建立信任。
怀疑私钥泄露时暂停发布、撤销相关 CI 权限和凭据，通过独立可信渠道告知操作者，
再完成公钥替换；签名本身不能补救已经取得发布私钥的攻击者。

## 验证边界

单测使用内存生成的测试密钥，覆盖篡改、未知密钥、缺签名及源码提交不一致。
隔离运行包验收使用临时仓库与测试密钥，不发布资产、不安装真实服务，
也不读取正式私钥。本批正式 CI secret、双平台附件及 Windows 实际安装
已另行核验；macOS 真机安装、应用代码签名和公证仍未验收。
